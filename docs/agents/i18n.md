# Languages

The client is available in English (the default), Dutch and German. All text of one language is in one file:
`src/i18n/locales/en.ts`, `nl.ts` and `de.ts`. Each is a flat object of `key: text`.

## Using text

```ts
import { t } from "@/i18n";

t("domains.register.title");
t("messages.count", { count: 3 }); // uses "messages.count.one" or "messages.count.other"
t("contacts.found", { id }); // "Contact {id} was found"
```

- `t` reads the language chosen on the Client screen. Screens remount when it changes, so call `t` while rendering, never
  at module load. Constants that hold text (menus, tabs, option lists) hold message **keys**, or are functions, and are
  translated where they are shown.
- Keys are written out in full as string literals (`t("a.b")`), never built from parts, so they can be found and checked.
  A table of cases keeps a key per case. A test fails when a key used in the code is missing from `en.ts`, or when
  `nl.ts` or `de.ts` have different keys from `en.ts`.
- Name keys `area.screen.what`, lower camel case, for example `domains.register.submit`.
- Plurals: give `key.one` and `key.other` and pass `count`.
- Text with a link or emphasis inside is split into keys for the parts, so the sentence order can differ by language.
- English is the fallback for a missing key, and the key itself is shown when English has none, so a gap is visible.

## What is not translated

Protocol identifiers stay as the server gives them: result codes, status values, field and property names, header names,
media types, paths, domain names, and anything the server sent (problem details, messages, titles). Developer tooling
that shows raw protocol data (exchanges, the raw request body and JSON) is not translated apart from its labels.
Text produced in `src/rpp` is diagnostic and stays English; that layer does not depend on this one.

## Adding a language

Add it to `LOCALES` in `src/i18n/types.ts`, add `src/i18n/locales/<id>.ts` with every key of `en.ts`, and register the
catalog in `src/i18n/index.ts`.
